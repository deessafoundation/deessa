## Batch gates and recovery

Every batch depends on Phase 4 and the previous numbered batch. This conservative order processes lower-risk domains first, then shell/media/finance, then program and event/conference editors. Sequential dependency does not require moving a whole subsystem at once: update all callers of each moved file atomically, leaving the remaining files at their current paths. Existing registry cycle members remain unchanged.

Entry: confirm the reviewed mappings, current source hashes/status, reference list, environment/test data and baseline diagnostics. Read the installed Next guide relevant to the edit and the full accessibility standards. Before execution, resolve any batch flagged SPLIT REVIEW into smaller numbered sub-batches; each owns its moved sources and all required caller edits. These flags block that draft batch from execution until the Phase 4 review refines it.

Exit: run the common validation gate and every listed profile; check every affected app-entry ancestor and layout descendants, all reference edits, casing, CSS, exports/directives and diff. Record commands/results and any pre-existing diagnostics. Fix migration-caused regressions before continuing; missing environment/runtime evidence leaves the batch incomplete. No check is claimed as run here.

Recovery: record a cleanly scoped pre-batch diff or snapshot before edits. If a batch fails, reverse only its tracked moves and import changes from that snapshot, preserving later/unrelated user edits; recheck status and affected behavior. Do not use reset --hard, broad checkout, folder deletion or overwrite destinations. If concurrent edits overlap, reconcile them before recovery. Never proceed to the next batch on an unresolved regression.

## Reference ownership

Each inbound import/re-export/type reference belongs to the batch moving its target. Each relative outbound import belongs to the batch moving its source. A reference may therefore be edited in two different batches; use the dependency paths current at that batch, not all final paths prematurely. `migration-mapping.json` records original specifier, resolved target, line, kind, type-only status, final source/target and owning batch. Recompute relative paths without changing binding kind or exports. References in KEEP/REVIEW files must still be updated when their dependencies move; their own location remains unchanged.

Jest mock paths for AssetPicker and SectionFormFactory have explicit ledger entries. Relevant Next config maintenance comments are also recorded. The computed data/programs loaders do not directly spell a moved component path: preserve loader behavior and update literal fixture imports through the ordinary ledger when demo-content is renamed. Never execute database migration scripts as a check. Preserve /astronaut.png, CSS selectors, registry/extension keys, routes and stored schema names. Historical docs retain old paths intentionally.
