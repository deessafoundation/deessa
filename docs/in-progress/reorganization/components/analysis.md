## Method and interpretation

The collector parsed 916 JavaScript/TypeScript source files outside documentation, dependencies, generated build output and agent folders. All 434 files returned by `rg --files` under `components/` are represented below: **396 TSX, 21 TS, 16 CSS modules and one PNG**. The root holds 34 TSX files plus five CSS modules. `admin/` contains 170 files, including 67 files directly at its root. There are 353 explicit `use client` directives and 119 filenames containing uppercase letters.

This is a syntax/import analysis supplemented by source inspection of system entry points, registries, route consumers and disputed files. It is not a claim that every implementation line was manually audited. Each profile records exports, imports, hooks and JSX extracted from actual source, not just a filename. All 434 files have explicit responsibility and candidate ownership annotations in reviewed-roles.cjs, reviewed against extracted source contracts, composition and consumers, with focused implementation reads for disputed systems. Categories are not inferred from the first route consumer. Candidate ownership is provisional; retention and final placement remain separate decisions.

The graph resolves root aliases, relative imports, index modules, re-exports, literal `import()`/`require()` and explicit type imports. Direct consumers include tests and type references; route ancestors follow syntactic non-type edges. A barrel can make all its exports appear reachable even if a particular export is not rendered. Regular imports used only as types can be elided by the compiler; only explicit type-only syntax is excluded here. Browser-name matches such as a local variable named `document` are signals, not proof of DOM access. No directive does **not** automatically mean server-only or server-compatible.

Additional searches covered registries, component path strings, test mocks, asset names and computed imports. Two computed require sites exist in scripts; they are described in the dependency map. Runtime CMS data and external consumers were not queried. No direct component-targeted dynamic import was found in the scanned source. Configuration-driven selection does exist, through the field registry and program renderers.

Usage labels:

- **USED**: a syntactic runtime import chain reaches an app entry point. This includes demos and error/loading entry points, and does not prove every exported symbol renders.
- **DYNAMICALLY REFERENCED**: selected from the conference field registry at runtime; imports are static but field selection is schema-driven.
- **LIKELY UNUSED**: no resolved incoming module edge in the scanned source. This is never permission to archive or delete; installed UI primitives may be intentionally retained.
- **UNCERTAIN**: type-only consumers, a disconnected consumer chain, or an asset needing non-import reference review.

There are **88 files with no incoming module edge** and **nine more with incoming edges but no app-entry ancestor**. These are analysis queues, not a deletion list. The 88 include the PNG; its public counterpart is discussed below. Exact direct consumers, import kinds and line numbers are in [component-details.md](component-details.md) and [component-evidence.json](component-evidence.json).

## System-level findings

### Public shell and shared presentation

`app/(public)/layout.tsx` composes navbar, footer, intro video, development notice, video-modal plumbing and accessibility controls. IntroVideo and DevelopmentNoticeModal are layout consumers, so classifying them as homepage-only is unsupported. NavbarWrapper fetches configuration before rendering the client Navbar. Footer owns the newsletter form; newsletter subscription remains a domain action even with a layout consumer.

Social icons cross public stories/podcasts, footer and admin forms. FormField/TextareaField are label/error wrappers shared by contact and volunteer flows via `components/form/index.ts`; they are a different abstraction from the React Hook Form implementation in `ui/form.tsx`. PhotoWall is used by public impact, admin settings and a demo; one file in a folder is not evidence that flattening is beneficial. ShareButton has one podcast-route consumer and hardcodes podcast-specific share text; classify it with podcasts rather than generic browser actions. Scroll animation helpers currently reach the homepage, not multiple proven domains.

### Accessibility

Panel, reading aids and dictionary are public-layout features backed by `contexts/accessibility-provider.tsx`, `lib/hooks/use-accessibility`, dictionary helpers and TTS services. Panel uses reading-guide stickers and TTS controls; the controls use panel primitives. Portal, DOM-selection, storage and speech behaviors make relocation sensitive to client boundaries and CSS. The feature has coherent local files but also important dependencies outside `components/`.

Accessibility tests exercise supporting logic; the absence of direct component test imports is not proof of no feature coverage. Existing standards remain mandatory. Do not combine moving components with global CSS consolidation or contrast repairs.

### Conference and events

ConferenceRegistrationForm uses DynamicStep and Step4Review. EventRegistrationForm reuses DynamicStep and StepProgressBar. DynamicStep and the event builder resolve fields through FIELD_REGISTRY. The same field system therefore serves public conference registration, public event registration and admin previews. Keep all 20 field implementations, their registry and schema contracts accounted for.

Conference step1/2/3 files still supply types consumed by Step4Review; the renderer functions have no runtime ancestor in this graph. Whole-file deletion based on JSX use alone would lose those types. DynamicFormRenderer currently has an admin-preview consumer, despite living under the conference public-looking directory.

EventFormBuilder also imports EnhancedConditionalEditor and FormTemplateChooser from the admin conference-builder directory. FormTemplateChooser actually calls event-module template actions. Folder name alone does not establish ownership. Existing event and conference APIs, conditional schemas, uploads and payment flows make this a high-risk migration group, not an opportunity to unify the implementations.

### Programs, templates and editor systems

CmsProgramRenderer selects campaign/outreach/research/service templates by category. Those templates use EditorialParts, SafeImage, related-program cards and shared content definitions. Production templates import `demo/programs.module.css`; CampaignTemplate imports `demo/campaign-concept.module.css`; EditorialParts imports CommunicationBoard from `demo/DemoInteractions.tsx`. Moving or archiving `demo/` as a unit would affect production and admin preview.

Most standalone public `programs/sections/*` renderers have no incoming edges; SectionHeading is referenced only by that disconnected group. RelatedProgramsSection is active through CmsProgramRenderer. This does not establish that every old section renderer is safe to remove. EditorialParts contains its own content-type switch; similar section names do not imply equivalent implementations.

The admin editor includes ServiceEditForm, EditorialProgramEditor, TemplateSectionsEditor, a section-form factory, asset selection, program context, history and media management. `program-sections/types.ts` also creates runtime defaults; it is not merely a type declaration file. `section-actions.ts` and event `builder-actions.ts` are local transformation helpers, not `use server` modules despite their names. ProgramEditorDemo intentionally imports admin editors from a public demo route with in-memory sample state. This boundary is a review question, not an automatic authorization vulnerability finding.

### Admin domains

Dashboard's barrel is used by `app/admin/page.tsx`; preserve the dashboard chart and data contracts. HomepageManagerClient in the nested directory is the active CMS and imports 17 local manager components (including StoryManager and WhatWeDoManager, absent from the older listing). The root homepage-manager-client has no incoming edge, but its imports include the active MediaPicker; archive decisions cannot propagate blindly to its dependencies.

Donation review components serve payments too. ActivityTimeline additionally serves support. ReviewStatusCard, ReviewNotesSection and StatusChangeModal explicitly depend on donation and payment actions. Those three belong to an admin finance candidate category; indiscriminate extraction to globally shared UI would carry domain actions with them. ErrorBoundary has a generic children/fallback contract. ActivityTimeline crosses finance/support while retaining admin activity semantics.

RichTextEditor serves stories and program rich-text section editing, retains its extension/dialog/hook system and imports story actions for image handling. That coupling must be preserved or separately reviewed. The media library, FileUpload and ConfirmDialog are used across admin features, while route-specific forms/actions have identifiable domain consumers. Record those domains instead of grouping all forms, actions and modals by widget shape.

### UI, hooks, errors and assets

UI has 74 files. Its direct component dependencies stay within `ui/`; no direct UI → feature/admin component import was found. This does not prove every file is domain-neutral. EventCard, StoryCard, ProjectCard and TeamMemberCard encode domain presentation. InitiativeCard and StatCard have generic presentation contracts, although their eventual location and retention remain open. Section is a generic spacing/container wrapper, and PrintButton calls browser print without a business dependency; neither must move merely because the old plan says so.

The mobile-hook copies and toast-hook copies are identical after newline normalization. No consumer imports the `ui/` copies. The hooks-level toast is still imported by project and volunteer admin actions. Both toast-hook copies expect types that `ui/toast.tsx` does not export; the unused `ui/toaster.tsx` also expects old Radix-style exports, while the current toast module exports a Sonner showToast API. This is a source-observed compatibility concern, not a new typecheck result, and should not be silently fixed during moves.

Error components serve real app boundaries and/or explicit demo routes. NetworkErrorPage and UnauthorizedErrorPage have demo consumers and are not unused. NotFoundErrorPage exports `NotFound`, so a filename rename must not mechanically rename its export. Its image URL is `/astronaut.png`, and `public/astronaut.png` exists; the same-named file under components is not resolved by that URL. Retain it pending asset review.

## Naming and CSS observations

Uppercase filenames occur throughout program renderers, editor systems, events, errors and homepage CMS. `EventFormBuilder/` is also a PascalCase folder. Hooks `useBuilderState.ts` and `useSectionState.ts` need explicit mapping in a later naming plan. Preserve public exports and internal identifiers; use kebab-case only after the complete current → target mapping is reviewed.

All 16 CSS modules have at least one resolved importer. Several deliberately have multiple consumers: homepage-sections.module.css serves HeroCarousel too; page-hero-contrast.module.css serves three routes; arts and podcast modules serve both route files and components; demo program CSS serves production templates. The per-file profiles enumerate each importer. `story-form.tsx` also imports global `app/print-styles.css`; do not treat it as orphaned based on the separate historical CSS analysis.

## Phase 1 review queue and Phase 2 follow-through

Phase 2 dispositions are recorded in [architecture.md](architecture.md) and the [dependency map](dependency-map.md). The following records the questions raised by Phase 1; it is not a claim that all architecture decisions remain open. Retention and exact destinations still require Phase 3 mapping.

1. Reconcile the existing direct feature-folder convention with a features layer; keep or change podcasts consistently.
2. Decide whether the common event/conference renderer stays in one domain with allowed dependencies or gains a dedicated schema-form boundary.
3. Decide ownership of production-used demo resources without changing their behavior.
4. Decide whether donation/payment/support shared admin pieces need narrower common modules.
5. Review public demo → admin editor dependencies and error demo consumers explicitly.
6. Review the 97 files lacking app-entry ancestry, distinguishing installed primitives, type-only contracts, inactive chains and assets. No archival decision has been made.
7. Choose placements for reviewed generic presentation contracts (StatCard, InitiativeCard, Section, PrintButton and form wrappers), the cross-domain PhotoWall and podcast-specific ShareButton. Contract review does not automatically justify moving them into ui/.
8. Record baseline toast compatibility and other existing check failures before any migration. Do not lower the validation bar or misattribute old failures.
